# BPF 项目模拟开发流程

这份文档用一个完整的模拟例子，说明当前项目里如何和 AI 协作完成一次业务开发。接入 Unity MCP 后，AI 不再只能读仓库，也可以直接读取 Unity 当前场景、层级和控制台状态。

适用场景：

- 新增一个业务步骤
- 修改一个题目交互
- 修一个 PICO 上才能复现的问题
- 排查 `_syc_resource` 老联机主线中的行为异常

## 1. 参与角色

### 你负责

- 提业务目标
- 指出模块、场景、对象线索
- 保持 PICO 设备连接，并允许需要的 Unity 构建和 `adb` 安装命令
- 在 Unity 或 PICO 上验证 Codex 安装后的版本
- 把真实现象反馈回来

### AI 负责

- 每轮新对话开始后，先执行 `git fetch --all --prune`
- fetch 后检查 `origin/main` 是否领先本地 `main`
- 如果有远端新提交，停止并询问是否拉取；未经同意不合并或变基
- 如果没有远端新提交，继续当前分支任务，不自动同步功能分支
- 工作区不干净时保护已有改动，只处理本轮目标文件
- 如果因为网络、权限、冲突或分支状态无法同步，AI 必须把失败命令、失败原因和你下一步该做什么直接说明白
- 每轮开始前先检测 Unity MCP 是否连通，并把连接状态直接说明给你
- Unity MCP 已连通时，优先读取仓库、文档、Unity 当前场景、层级和控制台
- Unity MCP 未连通时，本轮仍继续；避免 Unity-MCP-only 操作，改用仓库文件、命令行 Unity、`adb` 或其他本地工具推进
- 找真实入口场景和代码落点
- 修改脚本、prefab、scene、文档
- 每次完成会影响 PICO 运行行为的修改后，默认从副工程导出 APK，
  安装到所有已连接 PICO，并启动应用
- 处理模块资源时，先以 `Assets/...` 当前真实目录为准；`Assets/APP/MRTKSamples`
  是共享只读的上游示例依赖，`Assets/APP/Modules/LegacyMrtkSync` 是旧联机
  模块，只有任务明确涉及相应内容时才检查或修改
- AI 侧验证通过后先本地提交，不立刻推送
- 只有在你确认“验收通过”后，AI 才推送当前分支并创建 PR
- 如果无法导出或安装，明确说明具体阻塞原因
- 说明本轮改了什么，以及你要重点验证什么
- 每次对话结果出来后，都要直接告诉你下一步该做什么，不能只停在结果汇总

## 2. 模拟需求

假设这次需求是：

```text
模块：ServerAssembly
场景：WHY_FuWuQi.unity
问题：点击 U 盘后，系统安装面板没有正常显示
目标行为：点击一次 U 盘后，面板显示，并进入下一步
成功标准：PICO 上单次点击稳定生效，不能重复触发
已知对象：UPan、UI_XiTong、TaskUPan
```

## 3. 第一轮开发流程

### 第一步：你提需求

你把需求发给 AI，最好带这 6 项：

1. 模块名
2. 场景名
3. 目标行为
4. 成功标准
5. 已知对象或脚本名
6. 是否只在 PICO 出现

例如：

```text
模块：ServerAssembly
场景：WHY_FuWuQi.unity
行为：点击 U 盘后显示系统安装面板
成功标准：单次点击后进入下一步，不能连点重复触发
已知对象：UPan、UI_XiTong、TaskUPan
PICO / Editor：PICO 上问题更明显
```

### 第二步：AI 先同步仓库，再检测连接并判定任务类型

AI 每轮开始前都要先 fetch 所有远端并检查 `origin/main`。这一步先于读取仓库、
连接 Unity MCP、修改文件、构建和 git 提交。

默认执行顺序：

1. `git fetch --all --prune`
2. 检查本地 `main`、`origin/main`、当前分支和工作区状态
3. `origin/main` 有新提交时，停止并询问是否拉取
4. 没有新提交时继续当前分支，不自动合并或变基
5. 工作区有现存改动时保护它们，只提交本轮文件

如果同步失败，例如网络不通、没有权限、快进失败或分支不对，AI 必须先把失败命令和下一步动作告诉你，再继续决定本轮怎么做。

AI 收到后先判断 Unity MCP 是否已连通。

无论后面改不改代码，AI 每轮都会先把连接状态明确告诉你，例如：

- `Unity MCP：已连接，本轮继续。`
- `Unity MCP：未连接，本轮继续。`

如果已连通，AI 会先：

- 读取当前激活场景
- 读取相关根对象和层级
- 查看 Unity Console 中的报错和警告

如果未连通，AI 仍继续本轮任务；只是不能依赖 Unity MCP 读取现场，需要改用仓库文件、命令行 Unity、`adb` 或其他本地工具。

然后再判断这是哪类任务：

- 业务节点配置
- 题目 UI 配置
- 场景步骤树配置
- 模块脚本逻辑问题
- 遗留联机链路问题

这个例子里，通常会判定成：

- 场景步骤树配置
- 模块脚本逻辑问题

### 第三步：AI 定位修改点

AI 会先找：

- 真实业务场景
- 相关 prefab
- 步骤树对象
- 交互脚本

如果 Unity MCP 可用，上面这些对象和层级线索可以优先直接从当前 Unity 场景读取，而不是完全依赖手工口述。

这个例子里，常见落点可能是：

- `Assets/A_MRNet/Sence/03SingleplayerScene.unity`
- `Assets/A_MRNet/...`
- `Assets/Resources/BusinessPrefabs/...`
- `Assets/Resources/TopicPrefabs/...`
- `TexCore_StepObj`
- `TexCore_InteracterFunction`

### 第四步：AI 修改仓库

AI 会尽量只改和本轮需求直接相关的内容，例如：

- 修 `UPan` 点击后的状态切换
- 修 `UI_XiTong` 面板激活条件
- 修下一步任务推进脚本
- 修场景中的步骤树引用

这一轮改完后，AI 会告诉你：

- 改了哪些文件
- 改动目的是什么
- 你接下来该验证哪些现象

### 第五步：AI 导出安装，你验证

推荐固定顺序：

1. 在 Unity Editor 中进入目标场景
2. 先看点击 U 盘后面板是否显示
3. 再看是否推进到下一步
4. AI 从副工程导出 APK，安装并启动到已连接 PICO
5. 你在 PICO 验证真实设备表现

这里的顺序不会因为 Unity MCP 接入而改变。Unity MCP 可以帮助 AI 更快定位和缩小问题范围，但 PICO 真机结果仍然是最终验证标准。

### 第六步：你反馈结果

反馈格式尽量固定：

```text
结果：部分通过
实际现象：Editor 里能显示，PICO 上偶发点一次没反应
报错：无
发生步骤：点击 U 盘第一下
PICO / Editor：只在 PICO 出现
附件：录屏 / 截图
```

## 4. 第二轮开发流程

如果第一轮没有完全通过，流程继续。

### 例子

你反馈：

```text
结果：未完全通过
实际现象：PICO 上第一次点击没反应，第二次点击才进入下一步
报错：无
发生步骤：拿起 U 盘并靠近目标点后点击
PICO / Editor：PICO 独有
```

### AI 第二轮会做什么

AI 会根据现象缩小范围，例如：

- 检查 XR 交互事件是否只触发了 hover 没触发 select
- 检查碰撞体或交互层
- 检查 PICO 下是否存在首次激活延迟
- 检查步骤树状态是否被提前锁死

如果 Unity MCP 可用，AI 还可以先直接复查当前场景层级、控制台和对象状态，再继续修改相关脚本或场景配置。

### 你第二轮再验证

你再做一次：

1. Unity 简验
2. PICO 真机复验
3. 反馈结果

直到行为稳定为止。

## 5. 如果是老联机主线的问题

如果问题不是单机场景，而是 `_syc_resource` 老联机链路，例如：

```text
场景：Init -> UDPLobby -> Lobby -> MRTKsync
问题：客户端进入 MRTKsync 后看不到主机端物体显隐变化
```

那流程会改成：

1. 先确认是哪个场景阶段出问题
2. 再确认是 UDP 找房问题，还是 `MRTKsync` 同步问题
3. 再看：
   - `ExampleNetworkDiscovery`
   - `GlobalSyncManager`
   - `SceneItemSync`

也就是说，老联机主线的排查会比单机场景多一层“先判断断在哪一段”。

## 6. 每一轮结束时的标准动作

### AI 结束前

AI 应该给出：

- 本轮改了什么
- 改了哪些文件
- 这些改动想解决什么问题
- 是否已从副工程导出 APK、安装并启动到已连接 PICO
- 是否已经先做本地提交，并明确说明还未推送
- 如果没有完成导出安装，具体阻塞原因是什么
- 你下一步该如何验证
- 如果这轮已经完成验证，则明确告诉你可以继续提下一条需求

### 你结束前

你应该反馈：

- 是否通过
- 实际现象
- 报错
- 发生步骤
- 是 Editor 还是 PICO 才有问题

## 7. 一个完整的简版对话示例

### 你

```text
模块：ServerAssembly
场景：WHY_FuWuQi.unity
行为：点击 U 盘后显示系统安装面板
成功标准：单次点击后进入下一步
已知对象：UPan、UI_XiTong、TaskUPan
PICO / Editor：PICO 更明显
```

### AI

```text
Unity MCP：已连接，本轮继续。
我会先读取当前场景、层级和控制台。
我会先检查场景里的步骤树和 U 盘交互链，
重点看 TaskUPan、TexCore_StepObj、TexCore_InteracterFunction。
本轮会只修改 ServerAssembly 相关脚本和场景引用。
```

### AI（未连接示例）

```text
Unity MCP：未连接，本轮继续。
```

### AI 改完后

```text
本轮已修正 U 盘点击后面板激活条件，并避免重复推进下一步。
已从副工程导出 APK，安装并启动到已连接 PICO。
请重点验证：
1. Editor 中单次点击是否显示面板
2. PICO 上首次点击是否稳定生效
3. 是否还会重复推进
```

### 你验证后

```text
结果：部分通过
实际现象：Editor 正常，PICO 上第一次偶发不触发
报错：无
发生步骤：点击 U 盘时
PICO / Editor：PICO 独有
```

### AI 第二轮

```text
我会继续检查 XR 交互触发和首次激活时机，缩小到 PICO 设备差异相关逻辑。
```

## 8. 一句话总结

当前项目的 AI 开发流程不是“一次说完一次做完”，而是：

**你给业务目标，AI 每轮先做 Unity MCP 连接检测；能连 MCP 就读现场，不能连就用仓库文件、命令行 Unity 和 `adb` 继续；修改完成后默认从副工程导出 APK、安装并启动到已连接 PICO；你用真机结果推动下一轮修正。**
